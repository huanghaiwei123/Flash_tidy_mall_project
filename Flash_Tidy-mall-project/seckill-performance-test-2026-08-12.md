## 分析

### TPS 天花板：~1500–1700

TPS 没有随并发线性增长，瓶颈在 Redis —— 每个秒杀请求都要一次 Lua 脚本的 Redis 网络往返，Redis 在虚拟机上，网络 IO 上限决定 TPS 天花板。

### 延迟随并发线性增长

并发越高，请求在 Tomcat 线程池 + Redis 单连接里排队时间越长，但增长平稳，没有指数爆炸，说明架构没有死锁问题。

### 耗时分布（以 220ms 为例）

- Tomcat 接收 + 调度: ~10ms
- Redis Lua 脚本: ~5ms（关键路径）
- MQ 异步发送: ~5ms
- 排队等待: **~200ms**（线程池 + Redis 单连接排队）
- DB 写入: 不计入响应（MQ 异步消费端处理）

### 优化方向

| 优化项 | 预期效果 |
|--------|----------|
| 加 commons-pool2 启用 Lettuce 连接池 | 减少连接等待 |
| 调大 Lettuce max-active | 减少连接等待 |
| Redis 部署在本机 | 去掉虚拟机网络开销 |
| 增加 Tomcat 线程数 | 减少线程等待 |

### 结论

| 维度 | 评价 |
|------|------|
| 吞吐量 | TPS 1700，单机单 Redis 方案中等偏上 |
| 延迟 | 低负载 40ms，高负载 300ms，可接受 |
| 稳定性 | 6 轮仅 1 轮短暂 2.15% 错误，后续恢复 0% |
| 瓶颈 | Redis 虚拟机网络 IO + 未启用连接池 |
| 架构 | Lua 原子 + MQ 异步，设计正确 |

对于 JDK 8 + 单机 + Redis 虚拟机的学习项目，数据完全达标。
